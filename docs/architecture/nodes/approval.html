01 / RESPONSIBILITY

这个节点接收什么，交付什么？

INPUT / 输入

待审批 run_id；action_id、version、digest、approve；当前身份。

OUTPUT / 输出

批准：一个 committed 模拟工单并回填工具结果；拒绝：cancelled / rejected 且零写入。

02 / EXECUTION FLOW

代码是怎样一步步执行的？

  1. 01

    保存动作提议

    propose 将 run_id、工具名、规范化参数和版本绑定为 SHA-256 digest；任务进入 waiting_approval，释放执行租约。

  2. 02

    核验审批绑定

    approve 锁定运行记录和动作，校验 action_id、version、digest、状态与有效期。已提交或已拒绝动作重复请求返回原状态。

  3. 03

    批准时重查写权限

    在同一个事务中锁定当前权限行，检查 can_write，插入工单、更新动作结果，并把 committed / approved 的工具结果写回任务。

  4. 04

    恢复模型总结

    事务提交后路由重新 launch 同一 run_id；模型继续生成最终说明。拒绝则结束任务，不执行写入。

审批载荷示意
POST /agent/{run_id}/approval
{"action_id":"从 pending 读取",
 "version":1,"digest":"从 pending 读取",
 "approve":true}
重复批准同一动作 → 仍只有一张工单

04 / DESIGN BOUNDARIES

需要讲清的设计边界

幂等范围是本地同库

ko_agent_tickets.action_id 唯一，加上行锁与同库事务确保本地副作用。不能推广成跨外部系统的 Exactly-Once。

工单状态优先于回答措辞

模型总结失败或错误措辞不会撤销已提交工单。当前修复已让结果显式携带 committed / approved，新真实任务措辞尚待验证。
