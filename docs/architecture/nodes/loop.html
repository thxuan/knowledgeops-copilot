02 / EXECUTION FLOW

代码是怎样一步步执行的？

  1. 01

    先创建任务再执行

    create 保存任务与 accepted 事件，launch 启动协程，execute 取得数据库租约。重复 request_key 与相同消息返回原任务。

  2. 02

    请求模型并校验协议

    每次调用先预留 Token 和费用；校验工具白名单、严格参数、唯一 tool_call_id 和批次规则；相同规范化调用重复出现则 NO_PROGRESS。

  3. 03

    先保存 assistant 请求

    工具调用消息先作为检查点持久化，再执行工具；每个结果按同一个 tool_call_id 回填，模型才可以基于结果继续。

  4. 04

    验证最终输出

    FinalAnswer 要求 status 与非空 answer；失败最多追加一个关闭工具的格式修复轮次。运行结束保存 completed 与业务 outcome。

依赖调用示例
计算 17 × 23，再加 9
模型 → calculator(17, 23, *) → 391
回填结果 → 下一轮 calculator(391, 9, +) → 400
最终回答校验 → completed

04 / DESIGN BOUNDARIES

需要讲清的设计边界

status 与 outcome 分层

completed 也可能是 needs_clarification；业务工单已 committed 后模型总结仍可能失败。最终结果要同时查看 trace 与业务表。

两个 Agent 入口不要混淆

/agent/demo 是 Day 2 Fake 最小计算循环；/agent 是 PostgreSQL 持久化、多工具与审批链。

05 / TERMINOLOGY

专业术语 · 中英全名

中文 / 缩写英文全名在项目中的含义
智能体Agent在有界循环里依据中间结果继续选择工具；当前为自写单 Agent 执行器。
工具调用Tool Calling / Function Calling模型输出工具名与参数，服务端执行并通过 tool_call_id 关联回填结果。
检查点Checkpoint持久化运行消息、阶段、预算与结果，供同一个 run_id 恢复执行。
模式约束Schema / JSON Schema定义必填字段、类型、枚举和额外字段规则；Pydantic 执行运行时校验。
词元Token模型处理和计费的文本单位；项目的 UTF-8 字节预算是保守估算，不等于真实账单词元。
