01 / RESPONSIBILITY

这个节点接收什么，交付什么？

INPUT / 输入

当前问题、会话消息、原始用户记录摘要、检索 hits 与预算设置。

OUTPUT / 输出

system / user 消息、实际入选 evidence、历史 ID 与预算估算。

02 / EXECUTION FLOW

代码是怎样一步步执行的？

  1. 01

    先确定本轮检索问题

    当前显式错误码优先；指代问题从最近三条用户记录中选取主题，保留完整纠正。不是额外调用模型做通用查询改写。

  2. 02

    预留输出空间

    输入额度减去 output_limit 后才选择历史与证据；基础规则和当前问题已超限时直接报错。

  3. 03

    整条选择历史和证据

    从最近用户消息回溯，不跳过最新纠正去复活旧主题；证据按完整片段放入，有空间才补原始用户记录摘要。

  4. 04

    发送前复查证据

    ConversationRepository.check_evidence 再验证当前版本和授权，历史只帮助理解指代，不能作为本轮事实依据。

纠正优先
用户：TL-401 怎么处理？
用户：我说错了，是 TL-403。
用户：那接下来呢？
→ 检索补入最新的 TL-403 主题；事实依据仍来自本轮授权证据。

  24      # UTF-8 byte upper estimate + framing allowance, NOT billed provider usage.
  25      return sum(len(m["content"].encode("utf-8")) + 32 for m in messages) + 32

04 / DESIGN BOUNDARIES

需要讲清的设计边界

摘要不是模型编写的事实记忆

当前 summary 是带原始消息 ID 的用户记录，历史 assistant 答案不当作证据。Agent 则保留完整协议消息，采用独立预算机制。

估算不等于账单

estimate_tokens 使用 UTF-8 字节加开销；实际 provider usage 单独记录。

05 / TERMINOLOGY

专业术语 · 中英全名

中文 / 缩写英文全名在项目中的含义
词元Token模型处理和计费的文本单位；项目的 UTF-8 字节预算是保守估算，不等于真实账单词元。
UTF-8 · Unicode 转换格式 8 位Unicode Transformation Format — 8-bit文本编码；预算按编码后的字节数估算，因此字节数、字符数与 Token 数不同。
提示词Prompt模型的规则与任务输入；提示词约束不能代替服务端权限、校验和事务。
RAG · 检索增强生成Retrieval-Augmented Generation先检索本轮授权文档，再用证据生成回答；入口为 POST /chat。
