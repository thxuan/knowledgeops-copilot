02 / EXECUTION FLOW

代码是怎样一步步执行的？

  1. 01

    证据不足时直接拒答

    没有可用证据，或指代依赖的历史因预算缺失时，不让模型补猜；使用服务端固定拒答文本。

  2. 02

    模型只输出最小契约

    GeneratedClaims 严格要求 insufficient_context 与 claims 两个字段；每条 Claim 包含 text 与 citations。

  3. 03

    服务器构造最终响应

    parse_generation 校验结构，to_answer 用换行拼接结论并去重汇总引用；校验引用属于本轮上下文。

  4. 04

    最多一次格式修复

    结构错误可在同一授权证据下重试一次，并检查修复提示后的预算。仍失败标记 rejected；最终通过会话仓储原子提交。

模型输出形状
{"insufficient_context": false,
 "claims": [{"text": "一条有证据的结论",
             "citations": ["本轮真实 chunk_id"]}]}

answer 与顶层 citations 由服务端生成。

04 / DESIGN BOUNDARIES

需要讲清的设计边界

有效引用不等于语义支持

合法 chunk_id 只证明引用来自本轮证据，不能证明结论准确、完整或被原文支持；这些需要语义复核。

超时不提交半条回答

生成超时返回 GENERATION_TIMEOUT；会话提交还会复查版本、权限和并发版本。
