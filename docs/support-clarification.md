# 问答与 Agent 的澄清行为

问答与 Agent 共用 `app/core/support_policy.py` 的判断原则：区分关键用户条件缺失、适用证据不足、观测或执行能力缺失；先使用已有授权资料，必要时追问，不机械询问已知条件，也不把全部专用操作罗列给用户。

## 问答响应

模型仍只输出受校验的 JSON；新增可选 `follow_up`（空值表示无需追问，最多 500 字符）。事实留在 `claims`，每条必须引用本轮实际证据。追问是独立问题，不带来源 ID、不夹带事实结论或操作步骤。

- `answered`：有引用事实，没有追问。
- `needs_clarification`：有追问，可同时包含有引用的通用说明；也允许只追问，`answer` 为空字符串、`claims/citations` 为空。
- `refused`：适用证据不足，使用原有服务端资料不足提示，`follow_up=null`。
- `rejected`：输出格式或引用不合法，不保存未验证的追问。

对真实模型，未检出证据时也可生成澄清问题；任何事实结论仍必须引用本轮证据，没有证据就无法通过事实引用校验。明确将文档筛选为空列表时，保持原来的直接拒答行为。

追问轮跳过覆盖复查；下一轮正常回答仍沿用现有覆盖复查。问答只展示已校验的结论，保留对应引用与追问。

## 会话与权限

前端会话、运行详情和人工评审都独立展示“需要你补充”。原回答的事实文本和引用保持分离。追问写入现有会话消息与 payload，不新增数据表。

下一轮读取已授权的最近追问，将原问题、用户最近补充和本轮新输入一起用于检索。知识问答追问的短回复仍交由问答处理；Agent 沿用已有 `needs_clarification`。用户明确表示换个问题或换话题时，不再承接原追问；系统提示词也要求用户的新目标优先。

读取、模型调用、回放及提交阶段会重新核对追问来源的访问权限。后续消息保留来源依赖；文档撤权、撤回或版本失效后，相关旧回答与追问不能继续被当作可用内容。

## 验证和生效

针对性检查覆盖：独立追问与纯追问、事实引用约束、短回复承接、原上下文回放、来源撤权和前端纯文本展示。模型输出使用离线替身，不调用付费接口；真实模型能否准确判断缺失条件和适用性，需用当前知识库进行人工验收。

后端代码修改需重新启动后端进程生效，无需重新上传、向量化或重启数据库容器。模型密钥若仅保存在旧进程内存中，后端重新启动后需恢复模型配置。

## 决策顺序与回答范围（2026-10-20）

共享规则先明确目标和已知条件，再核对证据适用性，最后选择澄清、回答或拒答。问答提示词只有在条件充分且证据适用时才要求完整覆盖匹配分支，覆盖复查遵循相同顺序。

澄清轮最多保留 1～2 句必要通用说明，优先追问能改变下一步处理、排除不适用分支的条件；不展开条件未确认的专用建议。后续轮次围绕新补充推进，省略已经解释过的通用内容，不机械要求所有问题都询问操作系统。

本次只调整共享规则、问答提示词与复查提示词；不改变 API 字段、检索或会话存储，不增加模型调用。范围和适用性由模型遵循指令判断，并非服务端语义校验。真实效果需用现有资料人工验收：首轮未知系统时不展开系统专用分支；补充设备类型后不重述通用内容；确认系统但适用证据不足时拒答；条件明确且证据足够时直接回答。

## 适用条件与澄清范围校验（2026-10-20 后续修改）

真实模型的内部输出增加必填 applicability，包含按优先级排列的 conditions 和逐条对应 claims 的 claim_scopes。对外响应和已保存历史的字段不变。条件识别仍由模型负责，服务端校验其声明，不使用固定操作系统关键词路由。

confirmed 条件必须提供入模用户原话，且所需值逐字包含在该原话中；资料、历史助手回答与待补充问题不能确认用户条件。专用结论必须声明条件，未确认或不匹配的条件不能支持该结论。missing 条件的问题优先成为 follow_up，澄清轮只允许最多两条通用说明、总计不超过400字符。校验失败进入已有的一次有界修正，仍不合规则不展示该回答。

适用条件校验在跳过澄清覆盖复查之前执行，复查输出也重新校验。流式请求继续显示阶段状态，正文只在完整校验后显示；不再将已校验的结论替换为含其他分支的来源整段，避免输出处理绕过范围限制。

按用户要求，本次不运行自动化测试或付费模型验收；修改后重启 Python 后端，仅检查启动状态，由用户验收实际行为。模型可能漏报或误判适用条件，声明校验不能替代语义正确性验收。

## 逐条适用性与校验失败恢复（2026-10-20）

取代上一版“追问轮禁止所有条件性结论”的规则：逐条核对所需条件，已确认条件支持的结论保留，未确认或不匹配条件支持的结论删除。缺失条件继续形成追问，澄清轮仍限最多两条、合计400字符。删除结论后同步重新汇总引用。

applicability 新增必填 evidence_status（relevant/insufficient），拒答也必须提供评估。有相关资料但缺用户条件时转为追问；程序不再接受 applicability=null 的直接拒答。模型仍负责识别语义适用性，声明校验无法证明模型没有漏报条件。

rejected 使用专门的输出校验失败说明，refused 才使用资料不足说明。会话读取在最近20条消息内跨过 rejected，恢复上一条仍有权限的追问；成功回答或明确拒答结束追问，用户明确换话题也不会恢复旧追问。原有来源权限、撤回及固定上下文回放校验继续生效，不新增表或修改历史记录。

按用户要求，本轮不运行测试或付费模型调用；修改后重启后端，仅确认进程启动、健康接口和页面可访问，真实交互由用户验收。

## 用户原话与规范化条件值分离（2026-10-20）

修复 confirmed 条件强制要求 value 逐字出现在 user_quote 中的误拦截。程序仍验证 user_quote 确实摘自某一条入模用户原话，并要求规范化 value 非空；同义映射和条件匹配由模型负责，不再以子串关系证明语义等价。提示词明确允许“笔记本”规范化为“笔记本电脑”，禁止将“高速”擅自强化为“始终全速”等未确认细节。user_quote 本身仍必须真实摘录，不能规范化、拼接或伪造。

条件校验错误在会话 context.validation_failures 和结构化日志中增加服务端构造的字段路径与固定原因，例如 applicability.conditions[1].user_quote / quote_not_in_user_records。修正重试会指出具体字段，不记录原话、条件值或完整模型输出。校验原话来源仍不等于证明语义匹配，实际行为由用户验收。
