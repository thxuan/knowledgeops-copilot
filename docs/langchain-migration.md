# LangChain 生态迁移

迁移以现有业务行为为验收标准。每阶段先验证新实现，再删除被替代的自写实现。安装框架包本身不算迁移完成。

## 迁移前封存

2026-10-20 的实际工作区已封存到本机：

`D:/leetcode/knowledgeops-copilot-archives/20261020-180520-before-langchain/`

封存包含 6,167 个文件（包括未提交、新增、本地配置与 data 文件）、Git 历史、原依赖环境、整个 knowledgeops 数据库及集群角色定义。数据库通过一致性快照导出，在独立临时数据库执行 pg_restore，并核对 184 张表的行数。SHA-256 清单、恢复步骤和验证日志随封存保存，状态为 sealed。

此封存只在本机保存，包含私人数据及可能的凭据，不提交 Git 或上传外部服务。原 `.venv-knowledgeops` 保留，迁移使用独立 `.venv-knowledgeops-langchain`。内存中的连接 Key 需要重新配置，不能通过磁盘备份恢复。

## 保留的业务行为

| 领域 | 必须保持的行为 |
| --- | --- |
| 身份与权限 | 服务端认证；按租户、用户和工作区隔离；检索与输出复核文档授权；管理员无额外私聊读取权 |
| 文档与索引 | 原文件、版本、草稿、发布审批、撤回、有效索引头及已有向量；不因迁移重新调用 Embedding |
| 问答 | 未配置时报错；证据、引用及用户条件校验；格式修复有界；流式预览不等于正式提交 |
| 会话 | conversation_id、消息、标题、归档、分页、失效证据处理及并发 revision；保留完整原文 |
| Agent | 四种工具、参数与预算检查、取消、租约和恢复；打开历史不自动执行 |
| 工单 | 提案编辑、提交确认与业务审批相互区分；action_id/version/digest 绑定；并发或重试不重复建单 |
| API | HTTP/SSE 请求与返回契约、错误码、断开取消行为、用量与采样参数记录 |

## 第一阶段的实现边界

`app/core/langchain_models.py` 使用 ChatOpenAI 的 ainvoke / astream，生成与 Agent 的原公开适配器只保留应用契约转换。框架与供应商 SDK 的自动重试关闭，避免绕过现有 Agent 的预算预留与重试记录。流式输出仍须 stop 完整结束，服务端仍验证 claims 与引用后才提交。

供应商仍通过原 Base URL 和 Key 接入 Chat Completions。兼容参数 max_tokens 和 JSON mode 在请求体保留；JSON mode 不启用 SDK 的 parsed streaming，以保持底层分片接收与应用层格式校验；用户界面在完整校验后才逐字展示最终正文。模型用量保留原始缺失状态，不将未知费用记为零。非流式 Agent 输出保留原工具调用 ID、参数和结果配对。

LangSmith 依赖已安装，但外部追踪默认关闭；只有应用配置 KNOWLEDGEOPS_LANGSMITH_TRACING=true 时才允许 SDK 追踪。完整追踪脱敏、数据集和评测平台接入属于后续阶段。

原有模型接口测试中，缺少 assistant role 的 HTTP fixture 补为有效 Chat Completions 消息；SSE fixture 改为真实响应的单次消费语义；工具参数断言比较 JSON 语义，而不是空白序列。这些调整不改变业务预期。

## 验收与删除规则

1. 先跑迁移前离线回归，记录原有失败，不能宣称全部通过。
2. 模型适配器使用 MockTransport 等协议替身验证真实框架调用，不调用付费模型。
3. 数据库回归只使用临时 schema，不清空应用库、索引或历史。
4. 比较同一验收集合：原通过项目不得新增失败。新增覆盖流式取消、未知用量、预算重试边界等有意义的场景。
5. 本阶段覆盖的旧实现通过验收后才删除；其他模块继续保留并明确列入后续阶段。
6. 替身验证协议和控制流，不证明真实模型质量；真实供应商和用户场景验收另行记录。

原始测试日志保存在本机 `D:/leetcode/knowledgeops-migration/`；可公开的状态汇总见 [迁移证据](evidence/langchain-migration-20261020.json)。

## 开发与回退

新环境安装：`python -m venv ../.venv-knowledgeops-langchain`，然后使用其 Python 执行 `pip install -r requirements.lock`。原环境不升级、不删除。

回退第一阶段：从封存 ZIP 恢复本阶段改动的文件并使用原环境启动。此阶段不迁移业务表，不需要还原或覆盖当前数据库。只有需要恢复整个历史时间点时才使用全库备份，并先还原到新实例/新数据库，避免覆盖迁移后新增的业务记录。

## 2026-10-22 第三阶段：create_agent 用户验收通过

按用户指定顺序先做第三阶段，再做第二阶段长会话记忆。当前实现采用 langchain.agents.create_agent：框架承担标准模型/工具循环、工具分派、消息累积及终止判断；LangGraph 检查点提供持久执行和 interrupt / Command 恢复。初稿的自定义 StateGraph 已移除，保存在本机阶段备份中。

app/agent/service.py 创建 agent 并管理任务准入、租约、超时与取消；app/agent/middleware.py 通过模型和工具调用包装、before_agent / after_model hooks，执行费用预留、协议校验、有界重试、最终回答修复、旧任务接续与工单确认衔接。app/agent/chat_model.py 是单轮 BaseChatModel 桥接层，复用第一阶段 LangChain ChatOpenAI 接入及原有用量/错误契约。

四个工具注册为 StructuredTool。create_ticket 工具只返回已由确认 API 提交的事务回执；middleware 使用 interrupt 暂停，并在恢复时校验已提交回执及实际批准参数。框架恢复信号不构成业务授权。

框架消息、工具结果、节点输出和中断保存在新的 create-agent-v1: 检查点命名空间；业务库继续保存历史、预算、审计与工单事实。旧显式图检查点保留，未结束任务从最新业务事实接入 create_agent。已完成模型调用和只读工具的回执用于处理业务保存与框架保存间的崩溃窗口。
