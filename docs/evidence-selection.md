# 跨文档检索：覆盖选择与问题拆分试验

日期：2026-10-12。范围仅为检索与实际生成输入的证据选择。保持自然语言回答，不用整段摘录替代回答，不宣称引用语义已经正确。

## 实现

- `ranked`：原有单查询排序，是 `/retrieve` 和 `/chat` 的默认模式；聊天默认 Top20 保留。
- `coverage`：只检索原问题，候选默认20。去除重复 Chunk ID 和纯标题片段，在固定窗口里保留原排序的一部分直接证据，再按排名相关性、尚未覆盖的查询词、来源重复程度、正文相似程度挑选其余片段。来源多样性是软奖励，不强制每份文档名额。不改变原文或引用坐标。
- `multi_query`：在 coverage 基础上，真实模型用一次短调用产生最多3个互补需求；保留原问题查询，分别检索后用 RRF 合并，再选择同样数量的证据。Fake 只用标点分句，不代表真实语义拆分。
- 规划最多384输出 Token、10秒、一次调用；禁止新增数字/版本/错误码，支持30 MB与30MB这类空格差异。非法输出、超时、输入预算不足时回退原查询。空证据跳过规划。系统名称和需求是否忠实仍主要受提示约束，模型可能拆出多余需求。
- 每个子查询复用身份与过滤器，取当前授权候选；合并后按文档、Chunk Set和Chunk ID再次授权。补充查询失败记录降级，原查询失败仍失败。查询不授予任何权限。
- 选中的片段按选择优先级进入上下文，继续按整片段处理预算，不截断限制条件。诊断记录查询、规划状态与usage、检索run_id、原候选ID、合并候选及实际输入ID；生成次数不包含单独记录的规划调用。

这是基于查询词与排名的首版覆盖近似，不是语义证据蕴含判定，也没有实现父段落扩展。规则和权重根据开发案例调整，运行时不读取题号、gold来源、预期答案或评测锚点。

## 对照方法与结果

使用正在运行的本机18080服务、现有百炼配置和当前授权索引；不读取或保存Key。开发集20题、一次新检索，17题可回答，3题不可回答。每题原查询和子查询的候选池保存后，本地复用同一池做 Top5/8/10/20对照。各方法使用相同最终片段数及上下文预算；字符覆盖标签仅用于事后评分。没有生成答案。

全开发集报告：`docs/experiments/evidence-selection/20261012-130127-f71d57dc/`。

| 方法 | 跨文档必要来源齐全 | 可回答题平均来源召回 | 平均章节字符覆盖 | 平均输入估算 |
| --- | --- | --- | --- | --- |
| ranked@5 | 1/3 | 95.10% | 90.62% | 5,165 |
| coverage@5 | 2/3 | 96.08% | 87.44% | 5,349 |
| multi_query@5 | 2/3 | 98.04% | 91.18% | 5,332 |
| ranked@8 | 1/3 | 95.10% | 90.62% | 6,683 |
| coverage@8 | 2/3 | 98.04% | 91.62% | 6,978 |
| multi_query@8 | 3/3 | 100% | 95.13% | 6,951 |
| ranked@20 | 3/3 | 100% | 99.93% | 13,017 |
| multi_query@20 | 3/3 | 100% | 99.49% | 13,599 |

输入估算采用UTF-8字节加框架开销，非供应商计费Token。multi_query@8较ranked@20的平均生成输入估算减少46.6%，但关键章节完整度仍较低，不能宣称与Top20等效。

单独coverage@5出现章节覆盖倒退，因此不推荐单独将其替换默认。multi_query@20也没有比原Top20覆盖更好。当前有价值的方向是更小窗口下的组合方案，而不是把所有问题增加检索次数后仍塞20条。

追加跨文档3题复测：`docs/experiments/evidence-selection/20261012-130450-2716a695/`。同一版本multi_query@8仍3/3，平均章节覆盖77.57%；全开发集第一次的这3题平均77.57%。查询措辞与Top10/20细节仍有波动。另一次旧候选离线重算Top8未找齐，因此不能视为充分稳定性验收。3道题不是新的独立测试集。

## 代价与界限

全开发集新增20次规划调用，供应商usage合计5033 Token（prompt 4421、completion 612）；实际共65次查询检索，单查询基线会是20次。规划平均约2.03秒，完整新检索平均约6.46秒；没有同轮单查询耗时对照，不能给出延迟增量。Embedding用量和总计费仍没有从API暴露，降低生成输入不等于降低总费用。

本轮没有最终答案质量、拒答正确性或引用支持率成绩；不可回答题也参与检索，但不计来源覆盖均值。仍需检查否定条件、例外和决策权限等生成语义，以及新题和更多重复。默认保持ranked+Top20，两个新模式可显式启用进行下一轮问答对照。

## 使用

在18080服务的Swagger `/chat` 中可以提交：

```json
{
  "message": "你的复合问题",
  "top_k": 8,
  "retrieval_profile": "multi_query"
}
```

`coverage`用于只评估选择器，`ranked`用于原流程对照。同一字段也可用于 `/retrieve`；结果含完整诊断。

```powershell
& 'D:\leetcode\.venv-knowledgeops\Scripts\python.exe' -X utf8 scripts/compare_evidence_selection.py
& 'D:\leetcode\.venv-knowledgeops\Scripts\python.exe' -X utf8 scripts/verify_rag_api.py --top-k 8 --retrieval-profile multi_query --scope dev
```

第二条命令会调用真实模型生成答案，不是本轮已执行的验证。8000容器仍需重新构建才包含新代码。

## 耗时与实际用量补充

按保存的run_id只读查询数据库Embedding日志，20个原查询与65个合并检索调用均可完整匹配，均一次成功，没有额外模型调用。原查询Embedding共421 Token（每题21.05），原查询加子查询共964 Token（每题48.2）。问题拆分共5033 Token（每题251.65）。前三种单查询对照复用原查询池，不是三次独立执行；该部分Embedding平均每题1.161秒，完整单查询检索耗时未保留。组合方案Embedding累计平均3.753秒、规划平均2.027秒、完整检索平均6.455秒。以上都不含回答生成。

Embedding估算费用字段全部为NULL，因此金额未知，不是零费用。此补充恢复了实际Embedding Token用量，先前关于API未暴露用量的说明仍成立。完整审计见本次全开发集目录中的usage-audit.json。
