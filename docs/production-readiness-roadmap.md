# 从工程演示到内部试点：缺口与实施路线

评估日期：2026-10-18。代码基线：80931ac。

实施跟进：首批版本/发布/历史/ACL 展示已实现，实际契约与剩余限制见 [文档生命周期](document-lifecycle.md)。下文保留评估基线；后续已实现自有账号认证、管理员隔离、后台索引任务中心与基础工单闭环，见 [账号与后台业务](accounts-and-operations.md)；企业 SSO/MFA、配置持久化和生产运行验收仍待建设。

本次是源码、测试与文档静态盘点，没有重新运行真实模型、数据库回归、压力测试或生产安全审计。下文明确区分现有能力与建议实现；验收指标是拟定要求，不是已有成绩。

## 1. 定位与判断

项目已经有可复用的工程基础：授权检索、混合召回、引用校验、文档失效处理、多轮上下文、持久化 Agent、幂等建单、业务审批、数据库回归和 CI。主要缺口是知识生命周期、权限管理产品化、真实身份、运维与业务处理闭环。

建议下一目标是“可供一个企业部门受控试点的技术支持知识与工单系统”。初始规划按几十名用户、数千篇文档考虑，实际容量以压测为准。继续使用 FastAPI、PostgreSQL/pgvector 和单 Agent；优先补流程与边界，再用测量结果决定是否拆服务或增加基础设施。

## 3. 文档更新与历史版本应该怎样工作

### 3.1 当前实际行为

1. 已索引 v1 可以被授权检索和引用。
2. 上传者通过 PUT /documents/{document_id} 提交 v2 与 expected_version=v1。
3. 更新成功后，当前正文变为 v2，旧切块头立即失效；旧引用不再通过当前引用接口读取。
4. 在新切块和索引准备完成前，该文档暂时无法提供有效检索证据。
5. 构建完成后检索新版本；检索后和生成后还有版本/权限复核。

这条路径已经防止旧证据冒充新事实，但不能支持完整的历史原文查看。`tests/integration/test_vectors_api.py` 包含更新、撤权和失效检索测试；这次没有重新执行它们。

### 3.2 建议的目标流程

普通更新：编辑或上传新版本 → 保存草稿 → 解析与校验 → 后台构建索引 → 检查变更 → 发布 → 原子切换当前正文和检索版本。

普通更新构建期间，仍然有效且尚未撤回的旧发布版继续服务；构建失败不影响它。新内容在发布前不进入普通用户检索。发布时必须再次校验当前版本、管理权限与任务状态。

紧急失效：错误政策、敏感信息误发、文档撤回或权限撤销应立即阻断访问。不能为了可用性继续返回已撤回或已无权访问的旧版本。界面显示“已撤回”或通用不可用状态，避免泄露用户无权获知的文档信息。

内容状态与索引任务状态分开管理：草稿/已发布/已归档/已撤回是内容状态；排队/解析/向量化/校验/成功/失败是任务状态。向量生成成功不应自动等同于业务发布。

### 3.3 数据与接口建议

| 对象 | 建议职责 |
| --- | --- |
| documents | 稳定文档标识、所属空间、负责人、当前发布版本指针 |
| document_versions | 不可变的原始内容、清洗正文、版本 ID/标签、哈希、作者、变更说明、创建时间、来源与许可快照 |
| document_publications | 版本发布/撤回事件、操作者、原因、生效时间；与内容快照分离 |
| index_jobs / index_artifacts | 文档版本、模型签名、切块配置、阶段、租约、重试、成本、产物；复用已有切块/向量结构 |
| document_grants / audit_events | 授权主体、作用范围、变更原因与审计；首版可沿用用户 ACL，逐步增加组 |

建议增加：版本列表、版本详情、版本差异、创建草稿、构建任务、发布、撤回、以旧版本创建新草稿等 API。所有操作由服务端授权，版本 ID 为不可变标识，不能仅靠可重复的字符串标签定位历史。

版本回滚应“以 v1 内容创建 v3，再构建并发布”，保留 v2 的存在和回滚原因，不修改历史，也不恢复历史 ACL。

迁移时只能将现有当前正文建立为首个可验证快照；已有旧切块如需保留，标记为遗留片段，不能凭空恢复丢失的原文件或伪造发布时间。

### 3.4 搜索、引用和历史的产品规则

- 默认搜索与问答仅使用当前已发布且可访问版本；返回版本、更新时间、来源及定位片段。
- 历史浏览是独立入口，始终显示“历史版本”；旧内容不能默认为当前政策。
- 历史访问同时检查当前文档权限、历史查看能力，以及该版本自身的敏感范围；后来放宽当前版本权限不能自动开放旧敏感内容。
- 第一阶段先支持历史查看与对比；按时间点问答放后续，因为它还需要一致的多文档时间快照。
- 历史回答标明生成时使用的版本及当前是否已过期。重新提问按当前证据回答，不偷偷改写历史答案。
- 当前实现会对失效证据隐藏部分历史内容；引入历史浏览时应单独设计授权接口，不能放宽当前引用接口来绕过失效检查。
- 撤权后服务端读取、后续生成、前端缓存恢复与导出都需要复核；已被用户合法下载或复制的内容无法远程收回，应明确产品边界。

## 4. 谁可以看哪些文章

### 4.1 当前样例规则

下表来自 `sample_data/README.md`，描述样例预设，不是对当前运行数据库的查询结果。运行时以 document_access 中的实际授权为准；手动改过权限后，以新 ACL 为准。

| 样例文档 | 普通员工 | 工程师 | IT 支持 |
| --- | --- | --- | --- |
| 全员政策：账号/MFA、VPN、终端合规等 12 篇 | 可读 | 可读 | 可读 |
| 工程访问：KB-ENG-001 | 不可读 | 可读 | 不可读 |
| 事件分级与升级：KB-OPS-001 | 不可读 | 不可读 | 可读 |
| 自己新上传的文档 | 初始仅上传者；后续按实际共享授权 | 同左 | 同左 |

三个身份的 audiences 是样例受众说明；当前文档访问实际由用户 ACL 决定，并非完整动态用户组系统。文档正文中的“全员可见”等文字不能授予权限。IT 支持的工单审核能力也不意味着可以读取全部知识文章。

### 4.2 建议的权限模型和界面

权限拆成四个维度，避免简单的“高级身份可以做全部事情”：

1. 知识可见范围：租户/知识空间 + 用户/组织组 + 文档授权。
2. 知识管理能力：编辑、发布、撤回、管理授权、查看历史分别定义。
3. 工单能力：提交、分诊、权限审核、安全例外审核、生产变更审核、执行分别定义。
4. 平台管理能力：用户、连接、模型、配额、审计；系统运维管理员不自动获得敏感正文权限。

普通用户看到自己有权读取的文章；可以显示其本人获权原因，例如“工程组成员”。知识管理员能查看管理范围内的文档 × 用户/组矩阵、权限来源、变更前后差异。普通用户不应通过矩阵看到无权访问的标题和正文摘要。

权限检查覆盖列表、搜索、预览、原文、历史、差异、引用、问答、会话恢复、导出、Agent 工具和附件。不得仅在前端隐藏按钮。管理员的“以某角色查看”功能需要专属授权及审计，不沿用可任意填写的身份请求头。

## 5. 应补齐的八条可重复演示

每条演示都需要：隔离空间、固定输入资料、明确初始状态、页面操作步骤、预期结果、失败分支、检查证据和仅清理本次演示资源的重置方式。真实模型回答允许措辞不同，验收核对事实、引用版本和业务终态。测试替身不得冒充真实模型演示结果。

| 场景 | 操作与观察 | 核心验收条件 |
| --- | --- | --- |
| D01 文档更新改变答案 | 专用虚构 VPN 政策 v1 的刷新时间为 15 分钟，v2 改为 5 分钟；同题在更新前、构建中、发布后各问一次 | 草稿不泄漏；发布前可用的旧版与发布后的新版有清楚边界；新答案引用 v2；旧引用不冒充当前版本 |
| D02 历史对比与回滚 | 打开版本时间线、原文差异，按 v1 创建 v3 并发布 | 三个版本可审计；未覆盖历史；普通检索只用 v3；索引失败不改变当前发布版 |
| D03 同题不同身份 | 对工程访问、IT 事件分级分别用三个身份搜索和提问 | 结果符合样例矩阵；无权身份不能从标题、摘要、引用、历史或直接 URL 取回内容 |
| D04 撤权及时生效 | 已授权用户问答后撤销其权限；再次提问、点引用、刷新、恢复缓存、导出；加入生成中撤权 | 后续服务端访问和答案提交不得绕过撤权；缓存不重新展示受限内容；结果不能依赖清空浏览器才正确 |
| D05 更新/索引失败恢复 | Embedding 超时、构建任务中断、重复提交、并发编辑、重启恢复 | 有失败原因与重试；任务状态持久化；不发布半套索引；并发冲突可见 |
| D06 普通与敏感工单 | 普通问题提交；敏感请求转专属审核；自审、权限不足、重复点击分支 | 提交与审核分离；一次提交一个工单；批准不伪报已执行；补齐负责人到关闭的处理过程 |
| D07 历史会话遇到政策变化 | 多轮问答后发布新政策，再追问；打开历史记录并按原上下文重跑 | 标明历史证据已变化；新答案重新检索；重跑不修改原会话、不触发写工具 |
| D08 质量反馈闭环 | 用户标记答案过时/引用无关 → 管理员定位来源 → 修订发布 → 跑回归 | 反馈可追踪到修订版本和评测结果，不能以“请求成功”代替答案正确 |

新增场景页只负责导航、演示进度和结果核对，调用与正式页面相同的 API；不要另外写一套只在演示里成立的逻辑。未实现的步骤明确显示待建设，不展示假的成功状态。

## 6. 生产试点前必须补齐的工程边界

### 身份、数据和管理边界

- 用企业身份提供方接入 OIDC 登录，服务端验证可信身份；禁用生产模式的本地身份头，支持退出与账号停用。OIDC 是认证层，文档和工单授权仍由应用执行，参见 [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)。
- 连接/模型配置增加独立管理员授权；配置按工作空间持久化、版本化，密钥由受控密钥存储提供；供应商地址和出站访问采用受控配置。
- 对正文、历史版本、向量、缓存、日志、评测、附件和备份定义分类、留存、删除及供应商传输规则；公共仓库继续只保留已审查的样例。
- 建立跨租户与越权测试，特别检查对象 ID、导出和后台任务；提示词或模型判断不能代替后端权限。
- 工单分类的正则规则只作为演示分流提示。正式敏感操作应依赖结构化服务目录、资源与操作类型、服务端策略及审批职责。最小工具权限与下游执行授权遵循 [OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) 的建议。

### 可靠性与运维

- 使用有版本号的数据库迁移和升级兼容流程，替代仅在启动时建表补列；做升级前备份、失败恢复及发布回滚演练。
- 把索引作业持久化，复用现有 PostgreSQL 租约/重试思路；再考虑独立 worker。多副本前统一配置、限流和任务认领，不能直接增加 Uvicorn workers 后假定行为相同。
- 数据库连接池、任务并发上限、分页和资源配额按负载测试配置；记录各阶段耗时、供应商失败、重试成本和队列积压。
- 区分存活与就绪检查，增加模型/索引降级提示、指标、追踪和告警；不要每次健康探测都发付费模型请求。
- 对完整业务数据库与原文存储做定期备份和隔离恢复。样例备份验证不等于生产恢复能力；需要时间点恢复时使用与 PostgreSQL 17 对应的 [WAL 归档与 PITR](https://www.postgresql.org/docs/17/continuous-archiving.html)，并约定可接受的数据损失和恢复时间。
- CI 保留现有单元/集成测试，补浏览器端到端流程、迁移测试、依赖检查和构建验证；发布制品固定版本，告警有负责人及处理手册。

### 业务与质量

- 工单增加处理人、评论/附件权限、通知、处理与关闭状态；敏感审批按组织职责拆分，不能沿用演示中一个 IT 身份拥有全部审核能力作为生产组织设计。
- 第一条真实连接器优先接企业已有工单系统或只读资产查询；外部写入需要幂等键、事务出站记录、失败重试、结果对账和人工接管。
- 若未来接入设备/账号执行，再单独设计执行权限、审批有效期、执行时重新校验、回执与失败恢复；在此之前继续明确“批准但未执行”。
- 建立真实模型固定回归集：普通问答、跨文档、多轮、更新、撤权、缺证据、注入、超时、工具失败和敏感申请。分别报告正确性、引用支持、拒答、检索和任务终态，保留人工评审记录。
- PDF/DOCX、企业文档平台增量同步按真实试点资料优先级加入；接入时同时处理来源删除、ACL 同步、版本变化和解析质量，不能只做首次导入。

## 8. 验收口径

- 所有选定权限/租户/撤权/自审测试必须通过；这只是验收集结果，不宣称覆盖所有攻击。
- 新旧版本不混用、并发发布只产生一个有效结果、重试不重复建单，必须能通过自动化测试复现。
- 同一真实模型固定集独立记录答案正确、引用支持、合理拒答、Agent 业务成功率；测试替身结果单列。业务方评审后确定质量门槛。
- 压测记录用户数、文档/切块规模、并发、模型、硬件、P50/P95、失败率和费用；首个输出与完整校验后答案分开计时。
- 先测基线，再约定可用性、时延、成本、RPO/RTO 目标；没有负载和恢复证据时不承诺生产 SLA。
- 完成一次数据库/原文恢复、一次更新失败恢复、一次进程重启恢复、一次发布回退演练，保存脱敏证据与操作手册。
